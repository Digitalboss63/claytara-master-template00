# Claytara Digital engineering and site-maintenance protocol

This repository is the authoritative source for the Claytara Digital WordPress theme/site code. All coding agents, assistants, and automation tools must work from this repository and follow these rules before changing production-facing code.

## Source of truth and working-tree protection

- Treat `Digitalboss63/claytara-master-template00` as the authoritative Claytara website theme repository unless the owner explicitly changes that decision.
- Start every change with `git status --short --branch` and a targeted `git diff`.
- Treat unrelated local changes as user-owned. Do not overwrite, discard, or mix them into a feature commit.
- Keep changes focused, reviewable, and reversible.
- Work from current `main`. Before merging, compare the branch with current `main` and confirm the exact changed-file list.
- Do not create parallel "fixed" copies of the theme outside the repo as a substitute for committing the real change.

## WordPress/PHP discipline

- Preserve WordPress theme conventions and use WordPress APIs where available.
- Sanitize data on input and escape data on output using the appropriate WordPress functions.
- Admin/settings writes must use capability checks and nonces where applicable.
- Do not store credentials, API keys, analytics secrets, passwords, or tokens in the repository.
- Do not assume a plugin is installed unless the theme already requires it or the owner explicitly approves the dependency.
- Keep the theme usable when optional plugins such as Contact Form 7 are unavailable; fail gracefully.
- Do not change public URLs, template slugs, or existing content structure casually. Treat them as compatibility surfaces.

## Media and responsive-image rules

- Never force every image through one blanket `width:100%; height:100%; object-fit:cover` rule.
- Scope image behavior by use case: hero artwork, team/people photography, case-study thumbnails, product screenshots, logos/icons, editorial content, and embedded media may require different aspect ratios and crop behavior.
- Intrinsic `width` and `height` attributes must match the actual source asset dimensions or be generated by WordPress from the real attachment metadata.
- Preserve subject matter. Use `object-position` or a different presentation mode when `cover` would crop faces, text, devices, or other important content.
- Images must remain responsive on desktop, tablet, and mobile without stretching, overflow, or excessive vertical height.
- Prefer properly sized derivatives and modern formats such as WebP/AVIF when the deployment path supports them. Do not replace a source asset with a visibly degraded version.
- Use lazy loading for non-critical below-the-fold images where appropriate. Do not lazy-load the primary above-the-fold hero image when that would harm LCP.
- Embedded video/iframes must be responsive and must not overflow their container.

## Accessibility and site integrations

- Accessibility is a release requirement, not a cosmetic add-on.
- Preserve keyboard navigation, visible focus states, semantic headings, form labels, meaningful alt text, and adequate contrast.
- The authoritative location for third-party accessibility/ADA embed code is the Claytara admin Site Integrations/Accessibility setting. Do not create a second competing loader.
- Avoid duplicate ADA scripts when legacy and newer embed mechanisms both exist; consolidate to one authoritative path.
- Do not remove native accessibility behavior merely because a third-party widget is present.

## Claytara presentation rules

- Claytara should present as a credible product studio / automation and software company, not a generic template or an over-technical developer portfolio.
- Preserve clear human outcomes, plain-language value propositions, and relevant real-world imagery.
- Avoid decorative imagery that has no relationship to the service or product being described.
- Maintain a consistent visual hierarchy, spacing system, button treatment, card treatment, and media proportions across pages.
- New sections must be checked at common desktop, tablet, and mobile widths.

## Appearance, navigation, forms, and integrations

- Verify Light, Dark, and Auto appearance behavior wherever those controls/settings are exposed.
- Navigation must be tested on desktop and mobile, including menus, dropdowns, focus behavior, and active states.
- Contact/lead forms must be tested end-to-end when a live/staging WordPress environment is available. Confirm validation, success/failure messaging, and responsive layout.
- Site integration fields for accessibility, analytics, verification code, and approved head/body/footer snippets must save and render only in their intended locations.
- Never inject arbitrary code into both legacy and new integration paths.

## Debugging discipline

- Do not repeat the same failed action expecting a different result. After a failure reproduces, inspect a different layer: PHP error log, browser console, rendered DOM, network request, WordPress option value, plugin state, or active template.
- Before patching a visual or functional issue, identify the exact active template and CSS/JS rule responsible.
- Do not patch dormant or duplicate code because it looks similar to the active implementation.
- Prefer fixing the root cause over stacking overrides at the bottom of the stylesheet.

## Required verification before release

At minimum for theme changes:

- Run `php -l` against every changed PHP file; for broad changes, lint all theme PHP files.
- Run `git diff --check`.
- Inspect changed CSS/JS for syntax errors and duplicate/conflicting selectors.
- Verify no credentials or sensitive values were introduced.
- On staging or local WordPress when available, verify:
  - homepage and changed templates render without PHP warnings/notices;
  - desktop/tablet/mobile layout;
  - image sizing/cropping and responsive behavior;
  - navigation and mobile menu;
  - forms;
  - browser console;
  - Light/Dark/Auto appearance behavior if applicable;
  - Site Integrations settings, especially Accessibility;
  - key CTAs and internal links.
- A successful theme activation alone is not feature verification.

## Change reports and changelog

- Significant fixes and releases must update `CHANGELOG.md` with the user-visible behavior changed.
- Change reports should record the goal, files changed, verification performed, what was verified live, and what remains unverified.
- Keep reports concise and durable. Do not fill them with low-value activity logs.
